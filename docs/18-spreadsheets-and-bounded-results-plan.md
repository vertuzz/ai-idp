# Excel ingestion and bounded extraction results

Date: 2026-10-18. Status: **Research completed; production implementation proposed**.

## Recommendation

Keep the current 8,192-token generation ceiling. Plan each response to approximately
6,000 tokens, including evidence, and split work before generation. Add XLSX/XLSM
ingestion first, then XLS/XLSB behind an explicit capability matrix. Store independently
validated extraction parts and expose cursor-based result pages. Never require a model
to regenerate the entire combined list as the final merge step.

Input partitioning, bounded model output and HTTP result pagination solve different
problems. All three are needed. Streaming alone does not increase a generation limit.
This design applies to long PDF/DOCX arrays and nested schemas as well as spreadsheets.

Large workbook parsing and extracting every row are separate service capabilities.
Reading a million cells locally does not establish that a million records can be
extracted and independently verified within the existing request, cost and time budgets.

| Current behavior | Implementation | Consequence |

| Verification groups of 24 targets across every source batch | `pipeline.py::_verify_bounded` | Container values can still be huge; request growth is approximately field groups × source batches |

| Result retrieval requires a completed job | `application/use_cases/inspect_job.py` | Running-job partial results need a distinct contract |

Other effective limits are 250 physical model calls, 600 seconds and an estimated
USD 10 per job. The 256 MiB prepared-input limit and decoder's 1 GiB memory / expanded
data limits also matter. Existing limits must remain active during any continuation.

## 2. What the dependency already solves

The library used here is **Pydantic AI**, locked at `pydantic-ai-slim==2.57.0`.

- [Structured and streamed output](https://pydantic.dev/docs/ai/core-concepts/output/)
  supports validation and intermediate values. Intermediate streamed JSON is not a
  durable, independently complete extraction page.
- [Usage limits](https://pydantic.dev/docs/ai/core-concepts/agent/#usage-limits) constrain
  requests/tokens across a run. `ModelSettings.max_tokens` limits a generation;
  a usage ceiling does not schedule another result page.
- [IncompleteToolCall](https://pydantic.dev/docs/ai/api/pydantic-ai/exceptions/#pydantic_ai.exceptions.IncompleteToolCall)
  identifies truncated tool arguments. It does not implement collection coverage,
  item identity, resumable pagination or a lossless application-level merge.
- [Tool output limits](https://pydantic.dev/docs/ai/harness/tool-output-limits/) can move
  large **tool returns into the model** to external storage. This is a different
  direction from a large extraction **generated by the model**, and the separate
  harness is not a dependency of this project.

The application therefore needs its own bounded extraction protocol. Keep Pydantic AI
for typed calls and validation, and reuse existing job leases, request accounting and
checkpoints. A new orchestration framework is unnecessary for the first version.

Public [OpenRouter model metadata](https://openrouter.ai/api/v1/models), checked on
2026-10-18, advertised maximum completions of 128,000 tokens for the configured primary
model and 65,536 for escalation. These provider capabilities are not sensible application
defaults or quality guarantees. Actual endpoint capability and reasoning-token accounting
must be checked for the selected provider when executing a job.

A local `FunctionModel` simulated provider responses without network/model calls:

1. Truncated JSON + `finish_reason=length` led to four SDK requests with `retries=3`,
   then `IncompleteToolCall`. Repeating the same oversized task can consume the budget.
2. Syntactically valid, schema-valid JSON + `finish_reason=length` was accepted in one
   request. The application needs an explicit completion-reason guard even when JSON validates.
3. The equivalent response with `finish_reason=stop` was accepted normally. A normal
   finish also does not prove that every source record was extracted.

## 4. Excel ingestion design

### Format scope and parser choice

| Phase | Formats | Proposed implementation |
|---|---|---|
| First release | XLSX, XLSM | openpyxl read-only cell/formula view plus bounded OOXML metadata/media inspection; retain cached values separately |
| Next release | XLS, XLSB | python-calamine adapter, gated by format-specific evidence, date, formula and image capability tests |
| Compatibility extension | XLTX, XLTM, ODS, CSV/TSV | Explicit admission contracts and corpus cases; no blanket promise based on filename |

[openpyxl](https://openpyxl.readthedocs.io/en/stable/tutorial.html) provides OOXML
metadata and cell access; [optimized reading](https://openpyxl.readthedocs.io/en/stable/optimized.html)
reduces memory. It [does not evaluate formulas](https://openpyxl.readthedocs.io/en/stable/simple_formulae.html).
`keep_vba` is a preservation option, not macro execution. There is no need to preserve
VBA in a rewritten file because ingestion keeps the immutable original and never saves it back.
[python-calamine](https://github.com/dimastbk/python-calamine) offers broad read support;
its Python metadata/formula capabilities must be verified rather than inferred from the Rust API.

1. Extend content detection, the isolated-reader allowlist and settings serialization,
   composite-reader registration, unit kinds and preview contracts together. Detect
   OOXML workbook content types/relationships and distinguish OLE XLS from encrypted
   OOXML. Reject encrypted input with a specific capability error in the first release.
2. Preserve the existing isolated decoding process. Bound ZIP entries/expanded bytes,
   XML depth/text, actual populated cells, dimensions, shared strings, image pixels,
   sheets, generated units, memory and elapsed time. Ignore archive paths as host paths.
   Test patched/wrong worksheet dimensions and sparse far-corner cells.
3. Never execute VBA, XLM, DDE, external links, connections or formula functions.
   Keep links/formulas as inert source metadata. Do not fetch referenced resources.
   File protection and password encryption are separate states.
4. Store raw typed value, formula text, cached value and its type, number format,
   workbook date epoch, error values, merges, table/header relationships, hidden flags
   and source coordinates. Distinguish cached empty string, missing cache, blank and zero.
   Preserve leading-zero IDs and precision-sensitive numbers. Cache presence cannot
   prove freshness; expose calculation metadata and uncertainty.
5. Add `spreadsheet_range` units with immutable workbook/sheet identity and A1 ranges.
   Mechanically bound row/column tiles, repeat headers and declared context, and record
   which cells each unit owns. Models decide relevant sheets/regions, record grouping,
   column meaning and modality. Do not silently omit hidden/very-hidden content.
6. Retain embedded image anchors and supported image bytes. Expose chart/drawing or
   missing-render capabilities explicitly; provide a bounded cell-grid preview when
   visual evidence is required. That preview is not an Excel-faithful page render.
   Unsupported chart-only content must prevent a verified absence claim.
7. Use evidence locators containing document/sheet identity and exact cells/ranges,
   plus canonical text hashes/spans. Validate quotes and values against these artifacts.
   Cross-cell context is allowed; fabricated cell attribution is not.

Do not use pandas as the canonical representation: data frames alone lose workbook
layout, formula/cache distinctions, styles, images and precise evidence identity.
Defer Office-faithful rendering and recalculation to a separately evaluated adapter.

## 5. Bounded model responses and resumable parts

### Planning and completion

- Introduce a versioned extraction-part plan: schema fingerprint, field group,
  source scope, owned coordinates, context-only overlap, parent collection identity,
  immutable part ID, revision and job configuration. Plan hierarchical objects and
  nested arrays recursively. Root property count is not an output-size estimate.
- Group scalar/object paths within estimated output budgets. For collections, let
  models establish relevant regions and record boundaries; then partition those
  scopes into bounded output tasks. A scalar-only schema over a huge workbook should
  not trigger extraction of every row.
- Each response is complete structured JSON containing bounded items/fields, source
  anchors, evidence, processed scope and continuation metadata. The scheduler owns
  cursors and validates monotonic progress; a model's `has_more=false` cannot alone
  prove completion. Reconcile every assigned scope with a durable coverage ledger.
- Budget the schema, source, context, evidence and expected output. Retain byte/image
  guards and add token estimates with provider-aware calibration. Exact input+reserved
  output must fit the selected provider context; character counts are insufficient.
- Capture normalized finish reason and usage in the provider adapter. Treat `length`
  and `IncompleteToolCall` as incomplete work even if JSON parses. Split the task and
  retry the smaller scopes. Reduce same-shape SDK retries for deterministic size errors.
  Bound split depth, no-progress retries, total parts and physical requests.
- If one record/scalar is itself too large, split its fields or nested collection
  while retaining identity. If the smallest valid value still cannot fit, return an
  explicit unresolved/output-limit reason, never a shortened value presented as complete.

### Assembly, evidence and verification

Append validated parts from disjoint, model-resolved scopes through ordinary application
code. This is transport assembly, not a deterministic relevance decision. Give records
stable internal identities before generating final JSON Pointer indices. Preserve equal
but distinct business records. Eliminate replay/overlap duplicates only when immutable
source/part identity proves they are the same candidate, not because values happen to match.
Use bounded model reconciliation for ambiguous continuations or conflicts. Preserve
original evidence and candidate history. Never send all assembled items back for a final merge.

Replace whole-array verification requests with bounded candidate windows and explicit
collection coverage checks. Verify leaves and record associations against original source
units. Keep document-wide contradiction/coverage review and require every necessary scope
before confirming absence or collection completeness. A summary/hash of a large array
cannot substitute for source verification. Measure the cost of exhaustive cross-batch
verification before proposing scoped shortcuts; any change of verification guarantees
requires its own evaluation and documented policy.

Checkpoint each part, verification and coverage state, including failed attempts and
usage. Reuse existing job leases. Persist parts transactionally and make replay idempotent.
Separate stable candidate IDs from final list indices so a correction does not silently
retarget `/items/73/amount`. Budget exhaustion preserves completed parts but leaves
completion explicitly false. Expanding the 2,000-target cap comes only after bounded
target enumeration, storage and verification work; it is not a first-step fix.

## 6. Result delivery contract

Add endpoints alongside the current small-result endpoint:

| Proposed endpoint | Purpose |
|---|---|
| `GET /v1/extractions/{job_id}/result/manifest` | Revision, schema identity, known collections, processed/remaining scopes, completion and verification summaries |
| `GET /v1/extractions/{job_id}/result/collections?path=/items&cursor=...&limit=100` | Bounded collection pages with stable indices/IDs and a next cursor |
| `GET /v1/extractions/{job_id}/result/fields?cursor=...&limit=100` | Separate field/evidence/attempt pages |
| `GET /v1/extractions/{job_id}/result/export` | Incrementally serialized full JSON or record-oriented NDJSON export from stored parts |

Bind opaque cursors to job, revision and collection path. Use repository/database range
queries; do not load the entire result and slice it in the HTTP handler. Respect both item
and serialized-byte limits. A single item exceeding the page cap needs a documented bounded
field view or export path. Preserve global indices and ordering across nested collections.

Running-job pages expose only durable validated candidates and explicitly identify
provisional values, unverified fields, source coverage and revision. Never mix revisions
silently: return a specific stale-cursor response. A response page's validity does not
imply whole-document `schema_valid=true`. Final schema checks, including cross-part
constraints such as array size/uniqueness, remain separate from evidence verification.

Retain the existing endpoint for bounded small results; large results get an explicit
machine-readable link to paginated/export delivery rather than accidental giant responses.
Define and test this compatibility behavior before rollout. Optional SSE may announce
persisted part IDs/revisions and progress; reconnect uses durable cursors. Do not publish
unvalidated token fragments as extracted data. Existing `LimitedTransport` buffers the
response, so true token streaming would require a separate transport/accounting change.

Multiple files should initially remain one extraction job per file. A future batch
manifest can paginate child jobs, each preserving document identity, budgets and failures.
Cross-document joined extraction is a separate feature, not an implicit consequence of paging.

## 7. Initial limits to evaluate

These are proposed starting settings, not implemented defaults or calibrated guarantees.

| Control | Proposal | Basis |
|---|---:|---|
| Generation ceiling | **8,192 tokens**, retained | Existing default; provider-supported for current models |
| Planned response target | **6,000 estimated tokens**, including evidence | Leaves approximately 27% nominal headroom; estimate must be calibrated |
| First simple collection slice | **25 short four-field records maximum**, reduced for larger values | Experiment above uses approximately 4,659 proxy tokens; never a universal row count |
| 16,384-token generation | Explicit experimental profile only | Compare quality/cost; 100 sample records with evidence already exceed it |
| Text source tile | Target 4,000 estimated tokens; hard split before 8,000 | Starting hypothesis; retain headers, parent identity and owned-cell mapping |
| Model-request input | Keep 20 MiB / 12-unit byte/count bounds plus token/context guards | Bytes and unit count alone are inadequate |
| Result page | 100 items default, 1,000 maximum, 1 MiB serialized-byte cap | Independent from generation limits; oversized-item route required |
| New decoder controls | 128 sheets; 2 million populated cells; 10,000 units | Initial admission hypotheses, alongside existing memory/time/expanded-byte limits |
| Adaptive recovery | At most 8 split levels and 2 no-progress attempts per scope | Also subject to the tighter existing job-wide budgets |
| Physical requests / spend / wall time | Keep 250 / estimated USD 10 / 600 s | Do not silently multiply existing job budgets for large collections |
| Total extracted targets / stored result bytes | Explicit bounded settings; retain 2,000 targets until scalable phase passes | Raising limits now only moves the failure to verification or storage |

Run a feasibility estimate before expensive extraction and update it as record counts
become known. If predicted work cannot fit, return a clear budget/size response or require
an explicitly configured larger-job profile. Do not advertise unlimited extraction.
Do not use the current 256 MiB prepared-payload list for unbounded eager loading; move
prepared-unit loading to bounded iteration as part of large-job work.

## 8. Evaluation extension and acceptance

First establish a separate Excel development suite. Promote candidates into a versioned
corpus extension only after provenance, file-specific rights and label review. Keep the
paired templates, format conversions and size variants in the same family/split. The
existing 120 files remain regression cases; calibration/holdout are never used for tuning.

The 13 acquired files exercise parsing, not extraction quality. Still create project-owned
fixtures with parameter-derived, reviewable answers for:

- Flat registers at 25 / 50 / 100 / 400 / 1,000 / 10,000 records, with larger parser-only
  cases up to the configured cell cap. Keep large generated binaries ignored; commit only
  small project-owned fixtures and generation parameters after metadata review.
- Small and large scalar schemas, nested objects and multiple nested arrays, single long
  records, Unicode/long quotes, repeated true records and cross-boundary records.
- Multiple tables per sheet, merged/two-level headers, multiple sheets, hidden/very-hidden
  content, sparse sheets, wrong dimensions, huge shared strings and styles.
- Raw/cached formulas, valid cached empty strings, missing/stale caches, errors, external
  references, VBA/XLM markers, 1900/1904 date systems, locale-sensitive numbers and zero-padded IDs.
- Embedded-image-only values, chart-only information, invalid ZIP/OLE, encrypted files,
  archive/XML resource attacks, oversized cells and explicit capability limitations.
- JSON ending both validly and mid-value at the token limit; normal-stop omissions;
  replay, overlapping chunks, reordered responses, crashes before/after checkpoint,
  cancellation, stale cursors, budget exhaustion and source-hash mismatches.
- Large arrays from existing PDF/DOCX-style inputs so the design stays format-independent.

Offline acceptance: exact expected values/order and cell evidence on synthetic fixtures;
zero silently omitted records, replay duplicates or false-complete states; explicit
resource/capability failures; bounded request/page sizes; resumed output equals an uninterrupted
run; mechanical evidence failures remain unresolved. Parser counts alone do not satisfy this gate.

Live evaluation is a later explicit opt-in experiment with a supplied total spend ceiling,
development cases only and preserved failed-case denominator. Compare monolithic 8K,
monolithic 16K and bounded 8K under identical models, routing and evidence policies.
Measure item precision/recall, boundary-item recall, duplicate rate, evidence validity,
false completeness, schema validity, unresolved rate, truncation/retries, all-stage calls,
native input/output tokens, time and cost. Choose operating limits from these results.
An exhaustive 10,000-row live extraction is not assumed to fit the current defaults.

## 9. Implementation sequence and decision gates

1. **Evaluation extension and contracts.** Freeze development fixture families, expected
   values/evidence, partial/completion semantics and compatibility behavior. Add SDK
   completion-reason and size regression doubles. Done when failure examples reproduce
   without paid calls and source/label status is explicit.
2. **Small XLSX/XLSM ingestion.** Add detection, isolated range reader, formula/cache
   metadata, evidence and previews. Done when format/capability and decoder-resource
   tests pass on Windows/Linux/macOS; macros and external resources remain inert.
3. **Bounded output across formats.** Add field/scope plans, complete part envelopes,
   truncation splitting, durable identities and assembly without a full-list LLM merge.
   Done when scalar/array/nested-array cases survive limits, crashes and replay exactly.
4. **Scalable verification and persistence.** Remove whole-array request bottlenecks,
   enumerate targets/units incrementally and implement collection coverage checks.
   Only then evaluate higher per-job target/item/result caps. Done when evidence and
   absence guarantees pass and total-call forecasts match observed usage sufficiently
   to enforce the existing budgets.
5. **Paged API and exports.** Implement repository pagination, revisions, running-job
   provisional pages and compatibility limits. Done when large results can be inspected
   without full-result loading and resume/cursor tests pass.
6. **XLS/XLSB and live tuning.** Add calamine-backed capabilities and opt-in 8K/16K
   comparisons. ODS/templates, cross-file extraction and Office rendering remain separate
   extensions until their own evidence and quality gates pass.

No production extraction behavior or dependency lock was changed in this research.
The delivered changes are this plan, the pinned research-source metadata, a standalone
opt-in experiment script and its offline source-integrity/cache-classification tests.

Completed local checks: 23 parser probes across 13 sources, with only the two expected
encrypted-input rejections; 88 unit tests passed; lint and formatting passed; lock
consistency passed; worktree publication/metadata/fixture checks and changed-file
secret scanning passed. These checks establish research reproducibility and repository
hygiene, not live extraction quality or a calibrated operating limit.

## Reproduce

Run from the repository root. The first command validates existing corpus integrity.
The research command downloads only with `--download`; omit it for subsequent local
runs. It verifies pinned hashes on every run and makes **no live model requests**.
Optional parser/tokenizer packages are ephemeral, leaving `pyproject.toml` and `uv.lock`
unchanged. Pin production dependencies in both when implementing the adapters.

```text
uv run --locked --group evaluation python -m scripts.validate_corpus
uv run --locked --group evaluation --with openpyxl==3.1.5 --with python-calamine==0.9.0 --with tiktoken==0.14.0 python -m scripts.research_spreadsheets --download
uv run --locked --group dev --group evaluation python -m pytest -q tests/unit
```

The probe has 120-second child timeouts and samples memory; it is not a hardened
arbitrary-file decoder. It reads the fixed research catalog. Production ingestion
continues to require the isolated, memory-limited reader and decoder-specific guards.
